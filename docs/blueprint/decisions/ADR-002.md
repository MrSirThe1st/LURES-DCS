# ADR-002 — Phase 0 V1 decision lock

- **Status:** Accepted
- **Date:** 2026-09-11
- **Owners:** LURES-DCS engineering
- **Supersedes:** Open items in `PROJECT_KNOWLEDGE.md` §29 that this ADR explicitly locks

## Context

The operational V1 slice (import → Available → mobile verify/complete → realtime) is in place. Remaining product work needs locked decisions so implementation does not invent conflicting requirements. Phase 0 records those locks for the V1 completion track.

Out of this track: QR/barcode truck open (explicitly excluded). Offline-first mobile remains future (not V1).

## Decision

### 1. Permission matrix (V1)

Two roles only. Enforce with RLS + trusted use-case checks; never trust client-supplied role claims.

| Capability | Management | Loading staff |
|------------|:----------:|:-------------:|
| Sign in (own app) | Desktop | Mobile |
| View today’s trucks / bags | Yes | Yes (Waiting read-only until Available) |
| Import / create loading lists | Yes | No |
| Mark Available / Hold / Cancel | Yes | **No** |
| Verify / edit bags (reason on change) | View + authorized office edits if already allowed by existing UI | Yes |
| Complete truck | No (floor completes) | Yes |
| View audit / History | Yes | Truck-level events as already exposed on mobile journey only |
| Reports (lean summaries) | Yes | No |
| Export / print | Yes | No |
| Send (see §3) | Yes | No |
| Manage users (create, role, locale, disable) | Yes | No |
| Change own preferred locale | Yes | Yes |

**V1 rule:** Hold / Cancel are **management-only** (desktop). Mobile hold/cancel remains deferred unless this ADR is revised.

**V1 rule:** There is no separate “view-only management” role yet. If needed later, add it without weakening RLS for loading staff.

### 2. Export / print (V1)

- **Source of truth:** database truck + bags (+ verification/audit metadata as needed for the document).
- **Output:** PDF generated from structured data; print/save from the Tauri desktop app.
- **Layout:** company letterhead and liste-de-colisage structure close to the current digital truck detail / paper reference — **not** required to be pixel-identical on first ship.
- **Scope:** selected trucks from today’s overview and/or the open truck detail; prefer completed trucks, allow export of other statuses only if the UI makes status obvious.
- **Audit:** exporting creates an audit event.
- Excel/CSV remains import (and optional report CSV later); the primary “Export” nav action is PDF/print.

### 3. Send (V1)

**Send** means: from desktop, share the generated PDF via the OS (open mail client with attachment and/or system share) after Export-capable assembly.

**Not in V1:**

- WhatsApp or email server automation
- A new truck status such as `sent` / `dispatched`
- Cross-app “send packing list as file” (DB remains shared source of truth)

If stakeholders later want a “marked sent” flag, that requires a new decision — do not invent it during Phase 7.

### 4. Languages (V1)

| Topic | Lock |
|-------|------|
| Required locales | Mandarin (`zh`), English (`en`), French (`fr`) |
| Default UI language | **French (`fr`)** for new sessions / users without a preference |
| Persistence | `profiles.preferred_locale` |
| Switch UX | Language control on **Settings** (desktop and mobile); applies immediately for the signed-in user and updates the profile |
| Copy | Ship catalogs with keys; prefer confirmed glossary terms; do not invent Mandarin/French domain synonyms beyond existing UI English labels until glossary sign-off — interim translations may mirror current English operational wording |

### 5. Reports (V1)

Lean **operational summaries** on the desktop Reports screen only:

- Counts by truck status for a chosen date or date range
- Bag verification / modification counts
- Completion throughput if timestamps support it

**Not in V1:** advanced analytics products, performance BI, external monitoring suites (still out of scope per overview).

### 6. History (V1)

Full History replaces the stub: past loading lists/days, truck drill-in (reuse liste-de-colisage view), and filterable audit history. Today’s Loading screen remains the primary realtime surface.

### 7. Bulletin de pesage (V1 track)

**Deferred** from the active V1 completion track until stakeholders confirm a concrete cross-check workflow.

- Do not block Export, History, Users, i18n, Reports, or Send on bulletin import.
- Existing schema hints / import fields may remain; no new bulletin UX until confirmed.
- When promoted, treat as its own slice after core V1 items above.

### 8. Brand / design tokens

Keep current design tokens for feature work. Production palette and typography wait on stakeholder approval; do not block Phases 1–8 on brand.

### 9. Explicitly out of V1 completion track

- QR / barcode truck open
- Offline-first mobile (architecture must not forbid later)
- WhatsApp / email automation, weight-scale, OCR, multi-org, multi-site

## Consequences

- Feature docs and `PROJECT_KNOWLEDGE.md` §29 must reflect these locks.
- Implementation order remains: Export → History → Users/permissions → (skip mobile hold/cancel) → i18n → Reports → Send → CI/hardening; bulletin only if promoted.
- Revising hold/cancel for mobile, Send semantics, default language, or bulletin-in-V1 requires an ADR amendment or superseding ADR — not silent code changes.
