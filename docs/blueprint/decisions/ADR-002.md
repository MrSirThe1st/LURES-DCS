# ADR-002 — Phase 0 V1 decision lock

- **Status:** Accepted
- **Date:** 2026-09-11
- **Owners:** LURES-DCS engineering
- **Supersedes:** Open items in `PROJECT_KNOWLEDGE.md` §29 that this ADR explicitly locks

## Context

The operational V1 slice (import → Available → mobile verify/complete → realtime) is in place. Remaining product work needs locked decisions so implementation does not invent conflicting requirements. Phase 0 records those locks for the V1 completion track.

Out of this track: QR/barcode truck open (explicitly excluded). Offline-first mobile remains future (not V1).

## Decision

### 1. Permission matrix (V1)

Three roles. Enforce with RLS + trusted use-case checks; never trust client-supplied role claims.

| Capability | Management | Loading staff | Yard agent |
|------------|:----------:|:-------------:|:----------:|
| Sign in (own app) | Desktop | Mobile (floor) | Mobile (yard) |
| Import Loading Order / pre-alert | Yes | No | No |
| Close / cancel Loading Order | Yes | No | No |
| Confirm expected yard arrivals | Yes (desktop) | No | Yes (phone) |
| Register unplanned yard arrivals | Yes (desktop) | No | Yes (phone) |
| View yard queue / assign to a program date | Yes (desktop) | No | View arrived queue only |
| View today’s trucks / bags | Yes | Yes (Waiting read-only until Available) | No |
| Import packing lists (liste de colisage) | Yes | No | No |
| Mark Available / Hold / Cancel | Yes | **No** | No |
| Verify / edit bags (reason on change) | View + authorized office edits if already allowed by existing UI | Yes | No |
| Complete truck | No (floor completes) | Yes | No |
| View audit / History | Yes | Truck-level events as already exposed on mobile journey only | No |
| Reports (lean summaries) | Yes | No | No |
| Export / print | Yes | No | No |
| Send (see §3) | Yes | No | No |
| Manage users (create, role, locale, disable) | Yes | No | No |
| Change own preferred locale | Yes | Yes | Yes |

**V1 rule:** Hold / Cancel are **management-only** (desktop). Mobile hold/cancel remains deferred unless this ADR is revised.

**V1 rule:** There is no separate “view-only management” role yet. If needed later, add it without weakening RLS for loading staff.

### 2. Export / print (V1)

- **Source of truth:** database truck + bags (+ verification/audit metadata as needed for the document).
- **Output:** PDF generated from structured data; print/save from the Tauri desktop app.
- **Layout:** company letterhead and liste-de-colisage structure close to the current digital truck detail / paper reference — **not** required to be pixel-identical on first ship.
- **Scope:** selected trucks from today’s overview and/or the open truck detail; prefer completed trucks, allow export of other statuses only if the UI makes status obvious.
- **Audit:** exporting creates an audit event.
- Excel/CSV remains import (and optional report CSV later); the primary “Export” nav action is PDF/print.

### 3. Send (V1)

**Send** means: from desktop, share the generated PDF via the OS (open mail client with attachment and/or system share) after Export-capable assembly.

**Not in V1:**

- WhatsApp or email server automation
- A new truck status such as `sent` / `dispatched`
- Cross-app “send packing list as file” (DB remains shared source of truth)

If stakeholders later want a “marked sent” flag, that requires a new decision — do not invent it during Phase 7.

### 4. Languages (V1)

| Topic | Lock |
|-------|------|
| Required locales | Mandarin (`zh`), English (`en`), French (`fr`) |
| Default UI language | **French (`fr`)** for new sessions / users without a preference |
| Persistence | `profiles.preferred_locale` |
| Switch UX | Language control on **Settings** (desktop and mobile); applies immediately for the signed-in user and updates the profile |
| Copy | Ship catalogs with keys; prefer confirmed glossary terms; do not invent Mandarin/French domain synonyms beyond existing UI English labels until glossary sign-off — interim translations may mirror current English operational wording |

### 5. Reports (V1)

Lean **operational summaries** on the desktop Reports screen only:

- Counts by truck status for a chosen date or date range
- Bag verification / modification counts
- Completion throughput if timestamps support it

**Not in V1:** advanced analytics products, performance BI, external monitoring suites (still out of scope per overview).

### 6. History (V1)

Full History replaces the stub: past loading lists/days, truck drill-in (reuse liste-de-colisage view), and filterable audit history. Today’s Loading screen remains the primary realtime surface.

### 7. Bulletin de pesage (V1 track)

**Deferred** from the active V1 completion track until stakeholders confirm a concrete cross-check workflow.

- Do not block Export, History, Users, i18n, Reports, or Send on bulletin import.
- Existing schema hints / import fields may remain; no new bulletin UX until confirmed.
- When promoted, treat as its own slice after core V1 items above.

### 8. Brand / design tokens

Keep current design tokens for feature work. Production palette and typography wait on stakeholder approval; do not block Phases 1–8 on brand.

### 9. Explicitly out of V1 completion track

- QR / barcode truck open
- Offline-first mobile (architecture must not forbid later)
- WhatsApp / email automation, weight-scale, OCR, multi-org, multi-site

## Consequences

- Feature docs and `PROJECT_KNOWLEDGE.md` §29 must reflect these locks.
- Implementation order remains: Export → History → Users/permissions → (skip mobile hold/cancel) → i18n → Reports → Send → CI/hardening; bulletin only if promoted.
- Revising hold/cancel for mobile, Send semantics, default language, or bulletin-in-V1 requires an ADR amendment or superseding ADR — not silent code changes.

### Phase 4 closed (2026-09-11)

Mobile Hold/Cancel was **not promoted**. Phase 4 is closed as deferred:

- Floor status changes remain `available → loading` and `loading → completed` only (`canMobileTransitionTruckStatus`).
- Hold/Cancel stay desktop management actions.
- Do not add mobile Hold/Cancel UI without amending this ADR.


### Phase 8 closed (2026-09-11)

Bulletin de pesage import / cross-check was **not promoted** on the original V1 completion track.

### Operational document model (2026-09-13)

Amends the packing-list-centric wording above. Three documents remain three objects:

1. Pre-alert / Loading Order (`pre_alerts`) — expected trucks; lifecycle draft / active / paused / closed / cancelled. Pause makes the yard read-only for that order; delete removes expected trucks from the yard. `closed` is historical (no new closes).
2. Loading Program / BP (`loading_lists`) — not a packing-list bundle. Excel export reproduces the **company BP layout**, not a generic table.
3. Packing list — `trucks.packing_list_number` + `bags`.

Rules locked with this amendment:

- Physical vehicle identity (`vehicles`) is separate from an operational trip (`trucks`). Full vehicle registries may stay deferred.
- Arrival order (`arrived_at`), BP order (`program_sequence`), and actual loading order (`loading_started_at`) are independent.
- Preserve field provenance (`trucks.field_sources`: pre-alert / yard / BP / packing list / manual). **Never** silently overwrite yard-confirmed fields with conflicting BP data; show the conflict and let management resolve; keep previous/new values in audit history.
- Preserve transporter / client / driver / location **exactly as supplied** by each source document unless a user edits them. Do **not** introduce transporter-alias normalization as a matching requirement. Match pre-alert ↔ BP primarily by normalized horse registration.
- `organization_name_aliases` may exist for later linking; matching must not use it.
- External client representatives/checkers are `external_persons` (record who verified). No new auth role yet.
- Trucks that never arrived may exist as historical `did_not_arrive` from orders closed before pause/delete. Cancel expected or delete the order frees the plate. Pause does not free the plate; the yard cannot confirm or cancel until resume.
- Unplanned arrivals (yard agent + management) are allowed when the plate is not on a pre-alert.

Loading Program / BP Excel import and company-layout export shipped in **Phase 2** (2026-09-13). Management imports on Loading; unmatched horses may be created unplanned; yard-confirmed fields are never silently overwritten. Assign-to-loading-date remains a **bridge** for trucks not yet on a BP (`ensureActiveLoadingList` only uses lists with `bulletin_number IS NULL`). Do not parse packing-list sheets (装) as BP.

### Yard agent (2026-09-12, updated 2026-09-13)

Expected trucks come from Pre-alerts. The yard agent **confirms** those arrivals on the phone. Unplanned register is only for plates not on a pre-alert. Management desktop shows expected / arrived / did not arrive and may also register unplanned arrivals.

`loading_lists.packing_list_number` was renamed to `bulletin_number` in `20260913120000_loading_program_bp.sql` (`program_code`, `original_filename`, `storage_path` added). Per-truck packing list remains `trucks.packing_list_number`.
