# ADR-001 — Project Architecture and Monorepo Boundaries

- **Status:** Accepted (foundation)
- **Date:** 2026-09-03
- **Owners:** LURES-DCS engineering

## Context

The product needs a management web app and a mobile loading app sharing one operational backend (Supabase: PostgreSQL, Auth, Realtime, Storage). The system is for use in the **DRC only** and must support **Mandarin, English, and French**. Feature work must not start until package boundaries, design-token ownership, and auth/data access rules are clear.

## Decision

Use a **pnpm + Turborepo + TypeScript** monorepo with:

| Apps | Shared packages |
|------|-----------------|
| `apps/web` — Next.js App Router management UI | `packages/design-tokens` |
| `apps/mobile` — Expo (React Native) loading UI | `packages/domain` |
| | `packages/api-contracts` |
| | `packages/data-access` |
| | `packages/ui` (web primitives) |
| | `packages/config` |
| | `packages/utils` |

Backend platform: **Supabase** (PostgreSQL + Auth + Realtime + Storage as required).  
Auth provider: **Supabase Auth**.  
DB access: **PostgreSQL via Supabase**, versioned SQL migrations, generated DB types, RLS for authorization.

## Application responsibilities

| App | Responsibility |
|-----|----------------|
| `apps/web` | Management UI; Server Components by default; no service-role keys in the browser |
| `apps/mobile` | Loading-floor UI; talks to backend through safe client APIs/sessions; platform-native UX |

## Package responsibilities

| Package | Responsibility |
|---------|----------------|
| `design-tokens` | Single style source of truth (semantic colors, space, radius, type scales) |
| `domain` | Shared domain types/rules; no React; no DB queries |
| `api-contracts` | Shared Zod schemas / DTOs; no DB implementation |
| `data-access` | Server-side Supabase helpers/repositories; privileged access stays server-only |
| `ui` | Reusable **web** UI primitives consuming tokens |
| `config` | Shared TS/ESLint/Prettier bases |
| `utils` | Generic helpers only (not a dumping ground) |

## Dependency boundaries

```
apps → shared packages
data-access → domain, api-contracts
api-contracts → domain (types/schemas as needed)
ui → design-tokens (and utils if needed)
domain → (no React, no DB clients)
```

- UI must not own database access
- Mobile/web clients must not receive service-role credentials
- Prefer use-case-specific data access over speculative generic repositories

## Authentication approach

Supabase Auth with centralized session helpers. Distinguish authentication (who) from authorization (what) from domain rules (is this valid). Enforce authz server-side and with RLS.

TODO: finalize helper module paths and role claim mapping when auth is wired.

## Database approach

- Versioned migrations under `supabase/migrations/`
- Generated types rather than hand-duplicated table types
- No production schema drift outside migrations
- Excel/CSV is import/export only — never primary state

## Validation approach

Zod at external boundaries (forms, APIs, params, env, imports). Shared schemas live in `api-contracts` when genuinely shared.

## Consequences

- Clear ownership and progressive feature delivery
- Design tokens prevent divergent web/mobile palettes
- Slightly more setup than a single app; justified by two surfaces + shared domain

## Alternatives considered

| Alternative | Why not |
|-------------|---------|
| Separate repos per app | Harder shared domain/contracts/tokens |
| Single Next.js app only | Mobile loading UX is a first-class surface |
| Client-only Supabase with service role | Unacceptable security model |

## Rollout

1. Scaffold monorepo, tokens, empty domain/contracts/data-access/ui
2. Minimal runnable web + mobile shells
3. Wire Supabase local/project config without feature schemas
4. Implement features against docs thereafter

## Validation

- `pnpm install`
- `pnpm lint` / `pnpm typecheck` / `pnpm test` / `pnpm build` (as configured)
